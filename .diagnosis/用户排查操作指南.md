# 用户排查操作指南：后台播放"突然无声 / 进度不动 / 界面空白"

> **本指南面向普通用户**，不需要懂编程。
> 目的：让你在遇到问题时**把现场证据抓下来**，从而让开发者能定位原因。
> 适用版本：包含「运行时日志 + 后台心跳 + 原生诊断」的版本（设置页能看到"运行时日志路径"）。

---

## 一、先说明两件重要的事（相比上一版的变化）

1. **导出方式变了，而且变好了。**
   现在「**分享日志**」和「**复制诊断信息**」都会一次带上：
   - **本次启动**的日志（含启动时自动回捞的"**上一次启动**的最后 80 行"）；
   - **落盘日志全文**（跨多次启动，最多最近 1.5MB）；
   - **原生侧日志**（独立于界面线程，即使界面已经"死"了也仍然有记录）；
   - 即时状态快照（原生播放器状态/进度/队列、相关设置等）。
   → 所以你**不需要**再想办法去 App 私有目录取文件，点按钮就够了。

2. **故障后必须先重启再导出**（因为界面空白时进不去设置页）。
   这一点上一版写对了，但**当时代码并没有做到**（旧导出只含重启后的十几秒）。
   **现在是真的做到了**：重启后导出会包含上一次（出故障那一次）的记录，
   并且会明确写一行 `[SESSION] previous session did not end cleanly`。

---

## 二、复现步骤（尽量按这个来）

### 第 0 步：先确认日志功能正常
App → **设置** → 其他设置 → 「错误日志」区域：
1. 能看到两行路径（`日志文件路径` / `运行时日志路径`）；
2. 点「**查看运行时日志**」能看到内容（不是"日志是空的哦~"）。

> ⚠️ 这一步就没内容的话，先反馈这个情况，后面的复现没有意义。

### 第 1 步：记录并做一次对照实验（重要）
在 **设置 → 播放** 里记下当前取值：

| 设置项 | 说明 |
|---|---|
| **启用音频卸载** | **先按你平时的状态复现一次**；如果复现了，再**关掉它**复现一次。两次结果都告诉开发者（这是排查"无声但有播放状态"的关键对照） |
| **最大缓存大小** | 记录当前值（改完需重启 App 才生效） |
| **记住播放进度** | 建议开启 |

### 第 2 步：后台长时间播放（核心）
1. 打开歌单开始播放（建议随机/列表循环）；
2. 连续播放 **30～60 分钟**，中途可切歌几次；
3. 然后**切到别的应用**（或玩游戏）让 App 在**后台**播放 20～30 分钟。
4. 期间**不要清空日志**。

### 第 3 步：回来观察（把现象记下来）
- ☐ 是不是"显示在播放但没声音"？
- ☐ 进度条还动吗？
- ☐ 按播放/暂停/切歌有反应吗？
- ☐ **悬浮歌词**还在显示吗？它还会换行吗？
- ☐ 回到前台后界面是不是**空白**？（本版本会尽量把异常变成一条提示文字而不是纯白）

### 第 4 步：⚠️ 立即导出（最重要）
- 界面还能操作 → 直接导出；
- 界面空白/没反应 → **强制结束 App，重新打开**，然后**立刻**导出。
  （重启后导出的内容会包含故障那一次进程的记录，这正是本版本修复的点。）

## 三、怎么导出日志

### 方法 A：分享 / 复制（推荐，无需电脑）
设置 → 其他设置 → 「错误日志」区域：

- 点「**分享日志**」→ 会**在应用缓存目录生成一个 `.txt` 日志文件并调起分享**
  （可发到微信/邮件/云盘，作为附件提交最方便）。
  > 为什么改成文件：以前是直接把整份日志塞进"分享文本"，而系统对这种传递方式有大小上限，
  > 日志变大后会**直接把应用打死**（弹 "Critical Error Occured !"，必须杀进程重开）。
  > ⚠️ **如果你还在用旧版本，请先不要点「分享日志」**，改用「查看运行时日志」或「复制诊断信息」。
- 点「**复制诊断信息**」→ 复制一段**精简版**诊断到剪贴板（内容过长会自动截断并提示；
  需要完整日志请用「分享日志」的文件）。

两种方式都包含：即时状态 + 本次进程日志 + **上一次进程日志尾部** + **落盘日志全文** + **原生侧日志**
（「复制诊断信息」为控制体积会做裁剪）。

### 方法 B：查看后截图/复制
点「**查看运行时日志**」会显示**落盘的运行时日志（含轮转备份）**，
过长时只显示最近 20 万字符（完整内容请用方法 A 分享文件），可长按复制或分段截图。

### ⚠️ 两个"清空"别点错
| 按钮 | 作用 |
|---|---|
| 弹窗里的「**清空**」 | 清掉你当前正在看的那份日志 |
| 独立的「**清空日志文件**」 | 清掉运行时日志（会二次确认） |

> **导出之前不要点"清空"**，否则证据就没了。

## 四、日志怎么看（给开发者/进阶用户）

每行格式：
```
2025-01-01 12:00:00.123 INFO [TAG] 消息 key=value key=value
```

### 4.1 TAG 速查

| TAG | 含义 | 看到它说明什么 |
|---|---|---|
| `[SESSION]` | **会话边界** | `previous session did not end cleanly (killed, frozen or crashed)` = 上一次是被杀/冻结/崩溃，不是正常退出 |
| `[PREV_SESSION_RAW]` | **上一次会话的尾部原文** | 重启后也能看到故障那一次进程的最后记录（最多 80 行） |
| `[HEARTBEAT]` | **后台心跳（原生定时器）** | 后台期间每 30s 一条时间线；`heartbeat gap: JS thread was blocked or the process was frozen` = JS 卡住或进程被冻结；`player sample` 里带原生播放器的 state/position/duration/queueLen |
| `[PLAYBACK_SILENT]` | **"在播放但进度不动"** | 与"没声音但状态还是播放"直接对应，是最重要的新证据 |
| `[PLAYBACK_MISMATCH]` | UI 认为在播、原生状态却不是 Playing | 常见于状态事件被丢弃/丢失。**注意**：旧版本这里会每 30s 误报一次（判据取不到状态名，恒成立），新版本已修 |
| `[PLAYBACK_DURATION]` | 播放器报的 duration 异常偏短（<10s） | 进程被杀后重开时见过：`duration=2.194` ≈ 上一首 `queue-ended` 的 position，表现为"点播放瞬间结束" |
| `[RENDER]` | **界面是否还在更新** | 有 `progress rendered` = React 树活着；心跳还在但这里停了 = 界面已经不渲染（白屏的机制） |
| `[PLAYBACK]` | 播放状态机 | 包含 `state ignored by guard`（带 `gettingUrlIdAgeMs`）、`remote duck (audio focus changed)`（音频焦点被抢，以前完全看不到） |
| `[PLAYBACK_ERROR]` | **播放出错** | 含错误码与当前歌曲 |
| `[MUSIC_URL]` | 取链接 | 换源/缓存/失败原因；`urlWaitMs` = 取链接耗时 |
| `[STALL]` | JS 线程在前台被卡住 | 只在**前台**真卡住时才写；后台期间"定时器被系统暂停"不再误报（那条会写成 `WATCHDOG timer gap explained by host pause`） |
| `[WATCHDOG]` | 定时器诊断 | 见上 |
| `[BOOT]` | 启动过程 | 白屏卡在哪一步；`Navigation.setRoot start/done/failed` 是界面挂载的关键点 |
| `[FATAL]` | 崩溃 | JS/原生异常 + 播放上下文（含 `appState`/`uiVisible`） |
| `[APP_STATE]` | 前后台切换 | 何时进入后台/回到前台 |
| `[PLAYER]` | 播放器生命周期 | 初始化与切歌入口出口耗时 |
| `[MEMORY]` | 内存水位 | 正式版通常不可用，看不到是正常的 |
| **原生日志** | `ACTIVITY` / `TRIM` / `TP` / `JS_UNRESPONSIVE` / `NATIVE_GAP` / `SILENT_PLAYBACK` / `HEARTBEAT` / `AUDIO` | 见下 |

### 4.2 原生侧 TAG（独立于界面线程，即使界面已经"死"了也有记录）

| TAG | 含义 |
|---|---|
| `PROCESS start` | 进程启动信息（版本、SDK、机型、内存上限） |
| `ACTIVITY onCreate/onResume/onPause/onStop/onDestroy` | 界面生命周期（判断是不是界面被系统销毁/重建） |
| `TRIM onTrimMemory level=…` | 系统内存压力（玩游戏时常见） |
| `TP playback-state / playback-track-changed / playback-error / remote-duck / playback-queue-ended` | 播放器的原生事件（**不依赖界面线程**） |
| `JS_UNRESPONSIVE no JS ack for Xms` | **界面线程已经不再响应**（这是"界面空白但原生还活着"的铁证） |
| `JS_ACK resumed after Xms` | 界面线程恢复了，以及中断了多久 |
| `NATIVE_GAP heartbeat gap Xms` | 整个进程被冻结过（或主线程被长时间阻塞） |
| `SILENT_PLAYBACK state=PLAYING but no active audio playback for Xms` | **状态是播放、但系统层面没有音频在出声**（"没声音"的原生版铁证） |
| `AUDIO playbackConfigChanged` / `AUDIO_PROBE error` | 音频活跃度探针（后者说明该设备上探针不可用，需结合 `musicActive=` 判读） |
| **`THREADS dump reason=… threads=N jsFound=1/0`** | **界面线程失联那一刻的全体线程现场**（决定"卡死"还是"已消失"，见 4.5） |
| **`THREADS   @@ js name=… state=…`** | 界面（JS）线程的状态与完整调用栈（最多 48 帧） |
| **`THREADS   @@ js thread NOT FOUND`** | 界面线程**已不存在**（被杀死，不是被阻塞）——与上一行互斥 |
| `PLAYBACK_DURATION` | 播放器报告的 duration 异常偏短（重启后可能残留上一首的位置，表现为"点播放瞬间结束"） |

### 4.3 一条典型的"可由日志判定"的时间线

```
[APP_STATE] app state changed: background
[HEARTBEAT] tick seq=… appState=background isPlay=true …
[HEARTBEAT] player sample state=Playing position=123.4 queueLen=2
[PLAYBACK_SILENT] player reports playing but position is not advancing silentForMs=25000
（原生日志）SILENT_PLAYBACK state=PLAYING but no active audio playback for 26000ms musicActive=0
（原生日志）JS_UNRESPONSIVE no JS ack for 42000ms (JS thread dead or frozen)
```
→ 这类组合指向"原生音频管线停摆 / 播放器卡住"，并且能看出界面线程是何时一起失联的。

### 4.4 遇到空白界面时
本版本每个屏幕都有**错误边界**：渲染异常会被捕获，界面会显示
「界面渲染出错（已记录日志）」而不是纯白，日志里会有
`[RENDER] react render error caught by boundary ...`（含错误栈）。
若仍然是纯白，请优先看：原生 `ACTIVITY` 序列、`JS_UNRESPONSIVE`、`[BOOT] Navigation.setRoot` 三点。

### 4.5 怎么读 `THREADS dump`（本轮新增，最关键）

以前 `JS_UNRESPONSIVE` 只能证明"界面线程不应答了"，但**说不清是卡住了还是已经死了** ——
这两种情况修法完全不同。现在只要检测到不应答，原生就会**立刻抓一次全员线程栈**，
并在 60 秒阈值处再抓一次，所以先看第一行：

| 第一行里的关键字段 | 含义 | 下一步 |
|---|---|---|
| `jsFound=1` | 界面线程**还活着**，只是被卡住了 | 看紧随其后的 `@@ js … state=…` 与 `#0 #1 #2` 帧：它停在哪个 native 方法上，问题就在哪里 |
| `jsFound=0` + `js thread NOT FOUND` | 界面线程**已经不存在**了 | 不是死锁，是进程内 JS 引擎/线程被终止；重点看同一时刻的 `TRIM`、`PROCESS`、`ACTIVITY` 序列与内存字段 |
| **`jsFound=1` 且 JS 栈只有 `MessageQueue.nativePollOnce`（完全空闲）** | **JS 没卡住、也没在算，只是"没活干"** | 说明是**投递通道断了**，不是 JS 算不过来。继续看下面两行 |
| **`reactInstActive=0`** | **React 实例已销毁** ⇒ `BackgroundTimerModule.setTimeout` 里的 `hasActiveReactInstance()` 守卫为假，**所有 JS 定时器被静默丢弃且不会恢复** | 「投递通道断掉」的原因之一 |
| **`nativeModulesThread=0`**（配合 `mqtThreads=` 里只剩 `mqt_js`） | **RN 的 `mqt_native_modules` 线程已消失** ⇒ **所有 JS→原生调用**（定时器重排、ack、日志落盘）永远排队不执行 | 「投递通道断掉」的原因之二，且**比上一条更隐蔽**：实例还活着，调用却全部石沉大海 |
| 第二次 dump 的 `state=`、`reactInstActive=`、`nativeModulesThread=` 与第一次相同 | 稳定状态（不会自愈） | 对比两段 `@@ js` 的帧是否一模一样 |
| 出现 `JS_ACK resumed after Xms` | 自己恢复了 | 属于"冻结"而非"死亡"，看中间卡了多久 |

同一条 dump 里还会带上 `cacheDirMB`（播放缓存磁盘占用，会不会写满一看便知）、
`maxHeapMB`（Java 堆上限，`largeHeap=false` 时通常 256）、
`procUptimeMs`（**本进程**存活时长，注意别和 `uptimeMs` 混淆 —— 后者是**设备开机**时长）、
`reactInstActive`（React 实例是否存活：`1` 活跃 / `0` 已销毁 / `-1` 未知 / `-2` 无法探测）、
`nativeModulesThread` 与 `mqtThreads`（RN 队列线程是否存在、现存的 `mqt_*` 线程清单）。
另有 `QUEUE_THREAD` 一条独立日志，专门记录 `mqt_native_modules` 出现/消失的**翻转时刻**。

> **实测参考 ①（2026-10-19）**：`jsFound=1` + 栈全是 `nativePollOnce` + 两次 dump 完全一致
> ⇒ 判定为"定时器投递通道断掉"，而不是 JS 死循环或内存爆掉。
>
> **实测参考 ②（2026-10-22）**：同一形态，但 `reactInstActive=1`（实例还活着）⇒
> **推翻了当时的"实例被销毁"假设**；随后在 92 个线程里发现**没有 `mqt_native_modules`**，
> 于是把怀疑转向"native modules 队列线程消失"。这正是加 `nativeModulesThread`/`mqtThreads`
> 探针的原因：让下一次不必靠人工数线程名。

## 五、提交 Issue 时附什么

必须附上：
- [ ] **「复制诊断信息」的完整文本** 或 **「分享日志」的文件**（最重要）
- [ ] 手机型号 + Android 版本、App 版本号
- [ ] 现象勾选：不播放（无声音/进度不动） / 打开后空白 / 被系统杀掉
- [ ] 复现过程：听了多久、后台多久、是否在玩游戏
- [ ] **「启用音频卸载」开/关 两次的结果**、「最大缓存大小」取值
- [ ] 是否开着**悬浮（桌面）歌词**

强烈建议附上：
- [ ] `[PLAYBACK_SILENT]`、`[HEARTBEAT] heartbeat gap`、`JS_UNRESPONSIVE`、`SILENT_PLAYBACK` 的完整行（如果有）
- [ ] `[PLAYBACK_ERROR]` 完整行（含 code/message）
- [ ] 时间线（几点开始播、几点切后台、几点发现没声音、几点切回前台）

## 六、常见疑问

**Q：日志会不会越来越大？**
A：不会。运行时日志 512KB 轮转、保留 2 个备份；原生日志 512KB 轮转、保留 1 个备份。
合计上限约 2.5MB。

**Q：我点了"清空"会把证据删了吗？**
A：会。**导出之前不要点**。

**Q：为什么看不到 `[MEMORY]`？**
A：正式版通常没有 `performance.memory`，属预期行为。

**Q：为什么明明在后台卡了，却没有 `[STALL]`？**
A：`[STALL]` 只用于"**前台**界面线程被卡住"。后台期间 Android 会暂停 JS 定时器，
那是系统行为、不是故障，因此单独记为 `WATCHDOG timer gap explained by host pause`。
后台真正的卡顿/冻结请看 `[HEARTBEAT] heartbeat gap` 与原生 `NATIVE_GAP` / `JS_UNRESPONSIVE`。

**Q：日志里包含隐私吗？**
A：包含歌曲名、歌手、音源、播放状态、机型等；**不包含**账号密码。请勿删改内容。
