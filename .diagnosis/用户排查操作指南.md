# 用户排查操作指南：长时间听歌后「歌曲不播放 / 应用打开空白」

> **本指南面向普通用户**，不需要懂编程。
> 目的：让你在遇到问题时**把现场证据抓下来**，从而让开发者能定位原因。
> 适用版本：包含「运行时日志」功能的版本（设置页能看到"运行时日志路径"）。

---

## 一、这个功能是干什么的？

以前的日志**只记录扫描歌曲**之类的内容，出了问题几乎查不出原因。

现在新增了「**运行时日志**」，它会持续记录：

- 每次播放状态变化（播放 / 暂停 / 缓冲 / 出错）
- 每首歌的链接获取过程（有没有换源、有没有失败、失败原因）
- 预加载下一首的过程
- **JS 线程是否被卡住**（这是"假死"的关键证据）
- 应用启动的每一步（这是"打开后空白"的关键证据）
- 崩溃前的最后状态

**你要做的就是：复现问题 → 导出日志 → 提交。**

---

## 二、复现步骤（尽量按这个来）

目的是**让问题出现**，并且**在日志里留下痕迹**。

### 第 0 步：先确认日志功能正常（重要）
1. 打开 App → **设置** → 其他设置 → 找到「**错误日志（运行发生异常时的日志）**」这一项
2. 确认能看到两行路径：
   - `日志文件路径：...`
   - `运行时日志路径：...`
3. 点一下「**查看运行时日志**」按钮，**确认弹出的窗口里有内容**（不是"日志是空的哦~"）

> ⚠️ 如果这一步就没有内容，说明日志功能没生效，后面的复现就没意义了。请先反馈这个情况。

### 第 1 步：调整相关设置（让问题更容易复现）
在 **设置 → 播放** 里检查这几项：

| 设置项 | 建议 | 原因 |
|---|---|---|
| **启用音频卸载**（audio offload） | **保持你平时用的状态**（如果想试，可开启/关闭各测一次） | 该项在部分设备上会导致"音频加载出错""无法完整播放"，官方提示里也写明了这是系统 bug。**若你怀疑是它，请分别测试开启/关闭两种情况** |
| **最大缓存大小（MiB）** | 记录当前值（**改完需重启 App 才生效**） | 缓存设置影响长时间播放的稳定性 |
| **记住播放进度** | 开启 | 便于复现"续播"相关路径 |

> 💡 **关键**：请**记下你改动过哪些设置**，提交问题时一并说明。

### 第 2 步：长时间听歌（核心步骤）
1. 打开一个歌单，**开始播放**
2. 让它**连续播放至少 30～60 分钟**
   - 建议用**随机播放**或**列表循环**
   - 中途可以手动切歌几次
3. 期间**不要清空日志**

### 第 3 步：切到游戏（"玩游戏时更容易复现"）
1. 音乐**继续播放**的情况下，切到游戏玩 **20～30 分钟**
2. 让手机处于**内存压力较大**的状态（这是复现的关键条件）

### 第 4 步：回来观察
玩完之后切回 App，观察：
- ☐ 歌曲是否还在播放？还是"显示在播放但没声音"？
- ☐ 进度条是否还在动？
- ☐ 按播放/暂停键有没有反应？
- ☐ 如果 App 被系统杀掉了，重新打开是否**白屏**？

### 第 5 步：⚠️ **立即导出日志**（最重要，别拖）
**一发现异常，立刻去设置页导出日志。**
因为 App 可能随时被系统杀掉，**一旦被杀，内存里的日志就没了**。

导出方法见下一节。

> **如果遇到"打开后空白"**：此时可能进不去设置页。请**强制结束 App 再重新打开**，
> 然后**立刻**去设置页导出日志 —— 重启后的日志里会保留**上一次启动失败的原因**。

## 三、出问题了，怎么取日志？

### 方法 A：分享/复制（推荐，无需电脑）
1. 打开 App → **设置** → 其他设置 → 「错误日志」区域
2. 点「**分享日志**」按钮 → 选择任意方式发给自己（微信/邮件/保存到文件）
   - 或点「**复制诊断信息**」→ 粘贴到备忘录
3. 把得到的文件/文本提交到 GitHub Issue

### 方法 B：查看后截图/复制
1. 点「**查看运行时日志**」（会显示**完整的落盘日志，含备份**）
2. 长按文字可以**选中复制**
3. 也可以直接**截图**（内容较多时建议分段截图）

### 方法 C：用文件管理器取文件（需要能找到 App 私有目录）
- 设置页会显示实际路径，形如：
  - `运行时日志路径：/data/user/0/cn.toside.music.mobile/cache/runtime.log`
  - `日志文件路径：/data/user/0/cn.toside.music.mobile/cache/error.log`
- ⚠️ 这是 App 的**私有缓存目录**，**未 root 的手机通常无法直接访问**。
  → **请优先用方法 A 或 B**。

### ⚠️ 两个按钮的区别（别点错）
| 按钮 | 作用 |
|---|---|
| 弹窗里的「**清空**」 | 清掉**你当前正在看的那份日志**（看的是哪份就清哪份） |
| 独立的「**清空日志文件**」 | 清掉**运行时日志**（会二次确认） |

> **导日志之前千万不要点"清空"**，否则证据就没了。

## 四、日志里要看什么？（给开发者/进阶用户）

日志每行格式为：
```
2025-01-01 12:00:00.123 INFO [TAG] 消息 key=value key=value
```

**重点关注的 TAG（方括号里的名字）**：

| TAG | 含义 | 看到它说明什么 |
|---|---|---|
| `[PLAYBACK]` | 播放器状态机 | 记录每次 播放/暂停/缓冲/连接/就绪 状态变化 |
| `[PLAYBACK_ERROR]` | **播放出错** | **最关键**：包含错误码、当前歌曲 |
| `[MUSIC_URL]` | 链接获取 | 有没有换源、缓存命中、失败原因 |
| `[PRELOAD]` | 预加载下一首 | 预加载是否正常、是否卡住 |
| `[STALL]` | **JS 线程被阻塞** | **"假死"的直接证据** |
| `[WATCHDOG]` | 心跳看门狗 | 看门狗启动/停止 |
| `[BOOT]` | **启动过程** | **"白屏"的直接证据** |
| `[PLAYER]` | 播放器生命周期 | 初始化、切歌入口出口 |
| `[FATAL]` | 崩溃 | 崩溃前的完整上下文 |
| `[APP_STATE]` | 前后台切换 | 何时进入后台 |
| `[RUNTIME_LOG]` | 日志系统自身 | 日志轮转、写失败等 |
| `[MEMORY]` | 内存水位 | **注意：正式版通常不可用，看不到是正常的** |

### 每类 TAG 怎么看 / 下一步建议

#### 🔴 `[PLAYBACK_ERROR]` 播放出错
```
ERROR [PLAYBACK_ERROR] playback error code=... message=... trackId=... 
```
**含义**：播放器报告了一个错误。
**怎么做**：记录 `code` 和 `message`。
- 频繁出现且 `message` 提到链接/HTTP → **音源链接失效**，尝试**换源**或更换音源
- 提到 `decoder`/`codec`/`format` → **解码失败**，可能该音频格式不被支持
- 结合 `[MUSIC_URL]` 看当时是否**换源失败**

#### 🔴 `[STALL]` JS 线程被卡住（**"假死"的关键证据**）
```
ERROR [STALL] JS thread blocked for 25000ms durationMs=25000 lastEvent=... 
```
**含义**：JS 主线程被**卡住了 25 秒**（正常应每 5 秒打点一次）。
**这说明**：不是网络问题，而是**应用自己的代码把界面线程堵死了** ——
这正是"歌曲不播放 + 界面没反应"的典型机制。
**怎么做**：
- 看 `lastEvent` / `recentEvents` 字段 → **卡住前最后做的那件事**（如"正在取链接""正在切歌"）
- **频繁出现 `[STALL]` ⇒ 请务必把这段完整提交**，这是最有价值的线索

#### 🔴 `[BOOT]` 启动过程（**"白屏"的关键证据**）
```
INFO [BOOT] init step: xxx costMs=...
ERROR [BOOT] handleInit did not finish in 30000ms, home screen is likely blank
```
**含义**：记录启动每一步。若**卡在某一步**，就能知道白屏卡在哪。
**怎么做**：
- 找**最后一条** `[BOOT]` 记录 → 它后面那一步就是卡住的地方
- 若出现 `did not finish in 30000ms` → **初始化超过 30 秒没完成**，白屏确认
- 只看到 `app module loaded` 而没有 `font size & window size tools ready` →
  卡在了**很早的启动阶段**（该阶段没有 30 秒看门狗，属已知限制）

#### 🟡 `[MUSIC_URL]` 链接获取
```
INFO  [MUSIC_URL] try toggle to source source=... quality=...
WARN  [MUSIC_URL] url request failed, try next source plugin=... message=...
ERROR [MUSIC_URL] getMusicPlayUrl failed permanently
```
**含义**：记录取链接的全过程（缓存命中 / 换源 / 重试）。
**怎么做**：
- 大量 `try next source` → **音源不稳定**，建议换音源或更新源
- `failed permanently` → 所有音源都失败，**这首歌确实放不出来**
- `too many requests` → **被音源限流**，等一会儿再试

#### 🟡 `[PRELOAD]` 预加载
```
INFO [PRELOAD] preload next music start
WARN [PRELOAD] preload skipped, isLoading lock still held
```
**含义**：提前准备下一首（让切歌更顺）。
**怎么做**：
- 反复出现 `isLoading lock still held` → **预加载卡死了**（切歌会变慢/失败）
- 只有 `start` 没有 `done` → 卡在中间某一步（**注意：卡住时不会有任何日志**，因为代码停住了）

#### 🔵 `[PLAYER]` / `[APP_STATE]` / `[WATCHDOG]`
**含义**：播放器初始化、切歌入口出口耗时、前后台切换、看门狗状态。
**怎么做**：
- `[PLAYER] handlePlay calling setStop` 后面**没有** `setStop returned` →
  **卡在停止播放器这一步**（这是"点了播放但歌不播"的头号嫌疑）
- `[APP_STATE] app state changed: background` → 记录何时进入后台（用于判断是否被系统杀掉）

#### ⚪ `[MEMORY]` 内存水位
**注意**：该功能依赖浏览器提供的 `performance.memory`，
**在正式版 App 里通常不存在**，因此**日志里看不到 `[MEMORY]` 是正常的**，
不代表你的手机有问题。
（如果看到 `performance.memory unavailable` 这条 warn，属于预期行为。）

## 五、提交 Issue 时附什么？

请**逐项检查**：

### 必须附上
- [ ] **导出的日志文件**（或「复制诊断信息」的完整文本）
      —— **这是最重要的**，没有日志基本无法排查
- [ ] 手机型号 + Android 版本（设置-关于手机）
- [ ] App 版本号（设置-关于）
- [ ] **问题现象**（多选）：
  - [ ] 歌曲不播放（有声音界面但没声/进度条不动）
  - [ ] 应用打开后空白
  - [ ] 应用被系统杀死（后台被杀）
- [ ] **复现过程**：听了多久？是否在玩游戏？是否长时间后台？
- [ ] **你改动过的设置**（特别是「启用音频卸载」和「最大缓存大小」）

### 强烈建议附上（能极大加速定位）
- [ ] **出现 `[STALL]` 的完整段落**（如果有）
- [ ] **最后一条 `[BOOT]` 记录附近的内容**（如果是白屏）
- [ ] **`[PLAYBACK_ERROR]` 的完整行**（含 `code` 和 `message`）
- [ ] 出现问题时是否在**后台**/是否在**玩游戏**
- [ ] 是否**每次都复现**，还是偶发

### 如果可以，附上时间线
例如：
```
12:00 开始播放歌单（随机）
12:30 切到游戏
12:45 发现音乐停了，进度条不动
12:46 切回 App，按播放无反应 → 导出日志
```

## 六、日志等级怎么调整？

日志默认等级是 `debug`（记录最全）。

- **默认设置就够了** —— 不需要你手动调整。
- 如果开发者请你调整（例如怀疑日志太多影响性能），可以：
  1. 反馈给开发者，由其在代码里调用 `setLevel('info')`
     （可选值：`debug` / `info` / `warn` / `error`，级别越高记录越少）
  2. **普通用户无法在设置界面里直接调整**（本版本未提供该入口）
- ⚠️ **注意**：`[STALL]` 卡死日志用的是 `error` 等级，
  **无论怎么调等级都不会被过滤掉**，所以不用担心调高等级后丢掉关键证据。

## 七、日志会不会越来越大、占满空间？

**不会。** 新日志有**自动轮转**机制：

- 单个文件超过 **512KB** 就自动切分成备份（`runtime.log.1`、`runtime.log.2`）
- **只保留最近 2 个备份**，最旧的会被删除
- 因此占用的空间**上限约 1.5MB**（主文件 + 2 个备份），**不会无限增长**

> 这是相比旧版本（`error.log` 无限增长）的重要改进。

**如果你确实想清理**：设置页有「清空日志文件」按钮（会二次确认）。

## 八、常见疑问

**Q：我看不到 `[MEMORY]` 日志，是不是有问题？**
A：不是。内存采样依赖系统能力，正式版通常不可用，**看不到是正常的**。

**Q：日志里全是英文/代码，正常吗？**
A：正常。日志是给开发者看的，你不用读懂，**完整提交即可**。

**Q：我点了"清空"会不会把证据删了？**
A：会。所以**导出之前不要点"清空"**。
（已修复：现在弹窗里的"清空"清的一定是**你当前正在看的那份**日志。）

**Q：为什么复现不了？**
A：该问题与**长时间**和**内存压力**相关，可能偶发。建议：
- 听歌时间再长一些（1 小时以上）
- 确保玩游戏时手机内存压力较大（别先清理后台）
- 可以开着日志放着不管，出问题再来导出

**Q：导出的日志里有我的隐私吗？**
A：日志包含歌曲名称、歌手、音源名称、播放状态等。
**不包含**账号密码。提交前可以自行检查，但**请勿删改**，否则可能丢失关键线索。
